# Требования

## Функциональные требования MVP

- Пользователь подключает MetaMask к локальной сети Hardhat.
- Контракт выпускает Access Token (STK) и всю начальную эмиссию передаёт
  deployer.
- Пользователь оплачивает один из двух тарифов STK и получает продлеваемый
  срок доступа.
- Frontend показывает баланс и статус подписки.
- Backend проверяет подпись кошелька и on-chain статус перед обращением к
  локальному Ollama/Qwen.

## Параметры токена

| Параметр | Значение |
| --- | --- |
| Название | Access Token |
| Символ | STK |
| Стандарт | ERC-20 |
| Decimals | 18 |
| Начальная эмиссия | 1 000 000 STK |
| Получатель эмиссии | deployer |
| Дополнительный mint | отсутствует |
| Burn | отсутствует |

## Тарифы и продление

| Тариф | ID | Цена | Период |
| --- | ---: | ---: | ---: |
| MONTHLY | 1 | 100 STK | 30 × 24 часа |
| YEARLY | 2 | 1000 STK | 365 × 24 часа |

При действующем доступе срок тарифа добавляется к текущему `expiresAt`. Если
доступ истёк, срок отсчитывается от `block.timestamp`. Смена тарифа не
сбрасывает уже оплаченный остаток. Календарные месяцы и годы не используются.

## Нефункциональные требования

- Локальная разработка: Hardhat Network, без реальных криптоактивов.
- Node.js `>=22.13.0`, Hardhat 3 и только официальный Viem toolbox.
- Python `>=3.11`; на текущей машине обнаружен Python 3.13.11.
- Контракты должны быть покрыты воспроизводимыми тестами до интеграции UI.
- Секреты и приватные ключи не коммитятся; для конфигурации применяется `.env`.

## Границы MVP и безопасность

В MVP не входят NFT, DAO, RAG, AI-агенты, платные API, Redis, PostgreSQL,
лишние микросервисы и Docker. Проверка доступа в backend опирается на
подтверждённое состояние блокчейна, а не на значение, присланное клиентом.
