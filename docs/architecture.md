# Архитектура AI Token Access

## Назначение

AI Token Access — гибридная платформа доступа к локальной языковой модели.
Блокчейн фиксирует выпуск тестового ERC-20 токена STK, оплату и время
действия подписки. Модель Qwen запускается Ollama вне блокчейна. Поэтому
система не является полностью децентрализованной.

## Компоненты

| Компонент | Назначение |
| --- | --- |
| Frontend (Vite, HTML/CSS/JS, ethers.js v6) | Через EIP-6963 выбирает Trust Wallet, показывает баланс и подписку, инициирует оплату и чат. |
| Smart contracts (Solidity) | Выпускают STK, принимают оплату и хранят `expiresAt` для адреса пользователя. |
| Hardhat Network | Локальная тестовая EVM-сеть, используемая во время разработки. |
| Backend (FastAPI, Web3.py) | Проверяет подпись кошелька и статус подписки, направляет разрешённый запрос в Ollama. |
| Ollama + Qwen | Локально генерируют ответ модели через `/api/chat`; backend передаёт только запросы активных подписчиков. |

## Схема взаимодействия

```text
Trust Wallet ── транзакция ──> Smart contracts <── чтение состояния ── Backend
    ^                              │                                  │
    │                              ▼                                  ▼
Frontend <── баланс/статус ── Hardhat Network                    Ollama / Qwen
    │                                                                    │
    └──────────────────────── ответ чата ───────────────────────────────┘
```

## Границы on-chain и off-chain

On-chain: правила ERC-20 STK, перевод средств при покупке, тариф, событие
покупки и `expiresAt`. Off-chain: подпись для входа, HTTP API, управление
сессией, запросы к Qwen и текстовые ответы. Backend не должен доверять
данным о подписке, переданным frontend: он читает состояние контракта через
локальный RPC.

## Сценарий оплаты

1. Пользователь явно выбирает Trust Wallet, подключает его к локальной сети и получает тестовые STK.
2. Он выбирает MONTHLY или YEARLY и подтверждает требуемый вызов контракта.
3. Контракт списывает 100 либо 1000 STK и обновляет `expiresAt`.
4. При активной подписке начало нового периода — текущее `expiresAt`; иначе
   используется `block.timestamp`. Так остаток времени сохраняется.
5. Frontend и backend перечитывают подтверждённое on-chain состояние.

## Сценарий AI-запроса

1. Frontend получает подпись кошелька для авторизации в backend.
2. Backend связывает подпись с адресом и читает срок подписки из контракта.
3. Если `expiresAt` ещё не наступил, backend отправляет запрос в локальный
   Ollama/Qwen и возвращает только пользовательское поле `message.content`;
   иначе отвечает отказом в доступе. Служебное reasoning/thinking содержимое
   модели не передаётся пользователю.

## Ограничения децентрализации

Данные платежа и срока подписки проверяемы в блокчейне, но AI-вычисления,
авторизация, доступность backend и Ollama централизованы и off-chain.

## Локальная LLM-интеграция

`POST /llm/chat` требует HttpOnly-сессию SIWE и выполняет `hasAccess` через
backend перед каждым запросом. Он вызывает только `http://127.0.0.1:11434`
с `stream=false`, тайм-аутом и ограничением числа генерируемых токенов.
История сообщений не хранится сервером. При недоступности Ollama, неверном
формате ответа или ошибке blockchain API отказывает в доступе, а не выдаёт
ответ из кэша.
